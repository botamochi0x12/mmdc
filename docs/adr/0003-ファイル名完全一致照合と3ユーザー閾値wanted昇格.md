# ADR 0003: ファイル名完全一致照合と「3ユーザー閾値」によるwanted昇格

- Status: Accepted(現状追認 — 2026-07-04 にコードから逆起こし)
- 関連: [ADR 0002](0002-emm解析のサービス層同期実行.md), [ADR 0004](0004-集計照合クエリの生SQL実装.md), [specs/03-emm-upload.md](../specs/03-emm-upload.md), [specs/04-wanted.md](../specs/04-wanted.md)

## Context

emmファイルから得られるのはローカルPC上のファイルパスだけであり、
「どの配布モデルか」を直接識別するID等は存在しない。
同一モデルでも利用者ごとに保存場所が異なるため、フルパスでは同一性を判定できない。
また、誤操作や個人製作モデルなど「クレジット登録する価値のないファイル」も大量に混ざる。

## Decision

1. モデルの同一性は **`file_name` + `folder_name`(直上フォルダ名のみ) + `extension` の完全一致**で判定する。
   `mmd_objects` → `wanteds` → `credits` のJOINは全てこの3カラムで行う。
2. クレジット付け対象の管理単位として `wanteds` テーブルを置き、3カラムのユニーク制約で正規化する。
   `credits.wanted_id` もユニークであり、**wanted 1件 : credit 最大1件**。
3. 全ファイルを無条件にwanted化せず、
   **同一 `file_name` + `folder_name` を3人以上の異なるユーザー(動画の所有者)が使用した時点で初めて
   `wanteds` に登録する**(`EmmRegistService#is_wanted`)。
   なぜ閾値が「3」なのかは経緯不明(配布モデルと個人ファイルを分ける経験則と推定)。

## Consequences

- 配布モデルは通常フォルダ名・ファイル名を変えずに使われるため、実用上はこの一致判定で照合できる。
- 利用者がフォルダ名やファイル名をリネームすると別モデル扱いになる(既知の限界)。
- 3ユーザー閾値により、マイナーな配布モデルは利用者が3人集まるまでwanted一覧に現れない。
  昇格判定は**新規オブジェクト登録時のみ**行われるため、閾値到達後も
  「3人目のアップロード」が起きるまで昇格しない(過去分の再スキャンはない)。
- wanted昇格時の `extension` は3人目がアップロードしたファイルの拡張子が採用される
  (同名でも `.pmd`/`.pmx` が混在し得るが、is_wanted の集計は拡張子を条件に含めない)。
