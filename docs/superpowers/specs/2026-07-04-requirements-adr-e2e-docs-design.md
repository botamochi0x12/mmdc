# 設計: MMDクレジット 要件ドキュメント整備(ADR + E2Eテスト可能な機能仕様)

- 日付: 2026-07-04
- ステータス: 承認済み
- 目的: 純粋なドキュメント化(現行仕様の正確な記録)。テストコードの実装はスコープ外。

## 背景

MMDクレジットは、MikuMikuEffectのemmファイルからモデル・アクセサリ情報を抽出しDBへ保存し、
作者・配布先情報をユーザーが登録し、クレジット一覧をダウンロードできるRails 5.1アプリ
(Ruby 2.5 / MySQL 5.5)である。

- RSpec(controller/model)とMinitestが混在するが、E2Eテストは未整備
- `docs/` ディレクトリ、ADR、ドメイン用語集は存在しない
- Rails刷新や引き継ぎに備え、現行仕様を検証可能な形で記録する必要がある

## 決定事項

| 論点 | 決定 |
|---|---|
| 主目的 | 純粋なドキュメント化(将来のテスト実装や刷新の下地) |
| 文書構成 | `docs/adr/`(決定記録) + `docs/specs/`(GWT形式の機能仕様)に分離 |
| スコープ | 全機能網羅 |
| E2E基盤の想定 | 基盤中立のGWT + 各シナリオに「検証上の注意」を付記 |
| 仕様の分割 | リソース別(コントローラ/モデルとほぼ1:1) |

## ADRの書き方

各ADRは標準形式(Status / Context / Decision / Consequences)で記述する。

- 現状追認のADRとして `Status: Accepted(現状追認)` と明記する
- 「なぜそうなっているか」がコードから読み取れない箇所は推測せず、
  「経緯不明」または「コードからの推定」と区別して書く

## 仕様書テンプレート

```markdown
# 機能名
## 概要        — 1〜3文
## 用語        — この機能で使うドメイン用語(wanted, mmd_object等)
## 前提条件    — 必要なログイン状態・データ状態
## 振る舞い仕様 — シナリオごとに:
   ### S-01: シナリオ名
   - Given: 具体的な事前状態(データ値レベル)
   - When: ユーザー操作(URL・画面操作レベル)
   - Then: 観測可能な結果(画面表示・DB状態・リダイレクト先)
## 検証上の注意 — OAuthモック方法、emmフィクスチャの中身、
                 Windows-31J csvの検証方法など基盤中立の注記
## 実装参照    — file:line 形式でコードへのポインタ
## 未確認事項  — コードから断定できなかった挙動(あれば)
```

### E2Eテスト可能性の受入基準

1. 全シナリオの **Then が外部から観測可能**であること(画面・レスポンス・DB・ファイル)
2. **Given が投入可能なテストデータとして具体的**であること
   (「動画が存在する」ではなく「is_show=true, user_id=ログインユーザーの動画が1件」)

## 作成プロセス

1. 全コントローラ・モデル・サービス・主要ビューを精読し、既存のspec/testと突き合わせて挙動を確認する
2. ADR 8本 → 仕様書11本の順で作成する
3. セルフレビュー(プレースホルダ・矛盾・曖昧さ・観測可能性)を実施する
4. `docs/` をコンテキスト単位で分割してコミットする(日本語コミットメッセージ)

## スコープ外

- E2Eテストコードの実装
- リファクタリング・コード変更
- CONTEXT.md(ドメイン用語集)の作成 — 各仕様の「用語」セクションで代替する
